# Инструкция вставки server_next в Apps Script

Обновление онлайн-калькулятора до математики ред. 1.9 (единый модуль calc.js).
Папка `server/` — зеркало текущего боевого кода, она обновится **после** реального
деплоя. Вставка делается владельцем скрипта (eralmaz@gmail.com).

## Что в папке server_next

| Файл | Что это | Куда вставлять |
|------|---------|----------------|
| `calc.js` | Эталон модуля математики, **байт в байт = docs/calc.js** | Напрямую НЕ вставляется — эталон для сверки |
| `calc.html` | Тот же calc.js, обёрнутый в `<script>…</script>` | Новый HTML-файл «calc» в редакторе |
| `Калькулятор.gs` | Серверный код (doGet, getCalcData, findContract, fixSchedule) | Вместо текущего `калькулятор.gs` |
| `index.html` | Интерфейс ред. 1.9 (считает только calc.js) | Вместо текущего `Index` |

`Код.gs` и `НастройкаВалидации.gs` — **НЕ трогать**, они не меняются.

## Почему лист «График» менять не нужно (проверено по коду)

- Строки пишутся как «№ договора / дата / сумма / тип» (колонки A–D); тип —
  свободный текст в D, формулы файла его не используют. Новые типы
  («Первоначальный взнос», «Аванс», «Ежемесячный», «Финальный», «Договорённый»)
  ложатся в ту же колонку.
- Генератор ДДУ читает из «Графика» только дату и сумму — стартовые платежи
  со своими датами корректно попадают в таблицу договора.
- «План на сегодня» / «ПРОСРОЧКА» считают по датам строк — просрочка по каждому
  платежу от его собственной даты, ровно по ТЗ 7.4.

Меняется только **смысл** двух колонок «Договоров» (не структура):
- **«ПВ»** = сумма всех стартовых платежей (раньше — один первый взнос);
- **«Дата 1-го платежа»** = якорь ежемесячной серии (дата первого ежемесячного).

⚠ **«Ежемес. платёж» в «Договорах» — формула файла, витрина.** Для графиков
«От платежа» и с договорёнными платежами равного ежемесячного платежа не
существует (в контрольном кейсе — 18 × 1 500 и хвост 360): формула вида
«(стоимость − ПВ) / срок» покажет цифру, которой нет ни в одной строке графика
(например 1 440). Это терпимо, пока поле справочное. Если же «Ежемес. платёж»
или «ПВ» участвуют хоть в одном расчёте плана, просрочки или отчётов —
расхождение поедет в контроль. Проверка этого — пункт 3 полигонного чек-листа.

## Порядок вставки (важен!)

Расширения → Apps Script в боевом файле продаж.

1. **Создать HTML-файл «calc»**: «+» рядом с «Файлы» → HTML → имя `calc`.
   Стереть заготовку полностью, вставить содержимое `server_next/calc.html`
   **целиком** (включая первую строку `<script>` и последнюю `</script>`).
   Сохранить (Ctrl+S).
2. **Заменить `калькулятор.gs`**: открыть, стереть всё, вставить содержимое
   `server_next/Калькулятор.gs`. Сохранить.
3. **Заменить `Index`**: открыть HTML-файл Index, стереть всё, вставить
   содержимое `server_next/index.html`. Сохранить.

Порядок «calc → Калькулятор.gs → Index» гарантирует, что новый `doGet`
(он подключает файл «calc» через шаблон) не упадёт на отсутствующем файле.

4. **Деплой новой версии**: Развернуть → Управление развёртываниями →
   карандаш у активного развёртывания → «Версия: Новая версия» → Развернуть.
   **Без этого шага ссылка /exec продолжит отдавать старый код** — сохранение
   файлов само по себе ничего не публикует.

## Проверки после деплоя (по ссылке /exec)

1. **Контрольный кейс** («Прикидка»): площадь 62, цена 780, без скидки;
   стартовые: сегодня 1 000 + через 15 дней 20 000; режим «От платежа»,
   платёж 1 500, якорь — 5-е число следующего месяца. На экране:
   - ежемесячный **1 500 $**, «18 платеж(ей) … финальный: 360 $»;
   - контрольная строка **«48 360 $ = 21 000 $ стартовые + 18 × 1 500 $ +
     360 $ финальный ✓ сходится»**;
   - «Выровнять взносом» предлагает ↑ 21 360 (18 × 1500) и ↓ 19 860 (19 × 1500).
2. **Якорь 29–31**: якорь 31.12.2026 → серия 31.01, **28.02**, **31.03**, 30.04.
3. **Правило 10%**: сделать финальный платёж больше 10% стоимости (например,
   «Влить в последний» при большом хвосте) → красное предупреждение про
   согласование с руководителем.
4. **«По квартире»**: список подъезд → этаж → № грузится, статусы видны.
5. **«Зафиксировать» — сначала на полигоне** (копия боевого файла, по принципу
   «тест только в демо»): зафиксировать график с двумя стартовыми платежами и
   проверить глазами:
   1. в «Графике» строки со своими датами и типами (стартовые — не датой договора!);
   2. в «Договорах»: ПВ = сумма стартовых, «Дата 1-го платежа» = якорь, срок;
   3. **кейс с неравными платежами** (режим «От платежа» с хвостом, например
      контрольный: 18 × 1 500 + финальный 360): убедиться, что «План на сегодня»
      и «ПРОСРОЧКА» построены **от строк «Графика»**, а не от полей
      ПВ / Срок / «Ежемес. платёж». Проверка: на дату между якорем и вторым
      ежемесячным план должен быть равен «стартовые + 1 500» (сумма строк
      с наступившими датами), а не «ПВ + (стоимость − ПВ) / срок × k» —
      витринная формула дала бы 1 440, которых нет в графике. Если план или
      просрочка показывают числа, не совпадающие с суммой наступивших строк, —
      СТОП, формулы файла завязаны на справочные поля, сообщить Клоду до
      перевода на боевой;
   4. «План на сегодня» / «ПРОСРОЧКА» показали живые числа;
   5. «График: статус» = «на согласовании».

## После деплоя

Сообщить Клоду, что деплой выполнен, — тогда зеркало `server/` в репозитории
обновляется содержимым `server_next/` (до этого server/ не трогается).

## Локальный предпросмотр (по желанию)

В браузере GAS-скриптлет `<?!= include('calc'); ?>` не работает. Для просмотра
интерфейса без Apps Script сгенерировать файл с встроенным calc.js (git bash):

```bash
awk 'BEGIN{while((getline l < "server_next/calc.js")>0) c=c l "\n"} /<\?!= include\('"'"'calc'"'"'\); \?>/{print "<script>"; printf "%s", c; print "</script>"; next} {print}' server_next/index.html > tests/server_next_preview.html
```

Файл — одноразовый, в Apps Script его не вставлять, в репозиторий не коммитить.

## Что НЕ входит в этот этап

Контур брони (ТЗ ред. 1.4–1.9, разделы 8: «Оформить бронь», статусы, onEdit-страж,
автослёт, «Развить бронь в договор», тип «Зачёт брони») — отдельный этап.
В словаре типов calc.js «Зачёт брони» уже предусмотрен, но в интерфейсе руками
не выбирается (только автоподстановка при будущем развитии брони).
